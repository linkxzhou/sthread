# P1 / P3 / 128KB 栈 · 落地测量（2026-10-08）

实现提交 `a67127f`。改前对照是同一台机器上 `849ebf1` 的 [`perf-analysis-20261008.md`](perf-analysis-20261008.md)。不替代 `reports/baseline-curve.*`。

机器：Linux 6.12.94+，x86_64，4 vCPU KVM，Intel Xeon（家族 6 / 型号 207），16 GB，g++ 13.3.0，glibc 2.39，`nofile=524288`。曲线是 `make bench-curve`（`TRACE=0`，`DEBUG=1`，库 `-O1`，app `-O0`）。

## 硬指标

| 项 | 改前 | 改后 |
| --- | --- | --- |
| 空闲 `st_dnsserver` | 0.3 秒 30/30 tick，约 100% CPU | 1.0 秒 **0 tick**。`www.1.bench.local` 仍答 `127.0.0.1`，`fail=0` |
| 5 万短连接 VmSize（`-c 32 -n 50000`，`TRACE=1` 二进制，`LLOG_ERR`） | 约 272 KB/请求；2 万请求 13 MB → 5.2 GB | **12732 → 17792 KB，+5060 KB** |
| `strace -c` 挂上已启动的服务端，再打 2000 请求（`-c 30`） | `mmap` 2000；`epoll_ctl` 6134，errors 2000；`write` 4000；`rt_sigprocmask` 8201 | `mmap` **30**；`epoll_ctl` **4134，errors 0**；`write` **0**；`rt_sigprocmask` **4261** |
| 服务端 stdout | 每请求两行 `del event failed` / `del fd failed` | 只有两行监听横幅 |

`mmap` 30 约等于并发，不是请求数。`rt_sigprocmask` 从约 4.1 次/请求降到约 2.1 次，因为新建栈时的 `getcontext` 不再按请求发生。单测 `HttpServerVmSizeAfter50k` 用同一条 64MB 上限，不看 QPS。

## 短连接 QPS

`make bench-curve`，`n=50000`，3 次中位数，0 错误。提交 `a67127f`。原始重复在当次 `reports/curve-20261008-1251.*`（gitignore，不入库）。

| conc | 改后 QPS | p50 / p99 (ms) | 改前同机中位数 | 冻结 `e62c158` |
| --- | ---: | --- | ---: | ---: |
| 1 | 18464 | 0 / 1 | 20276 | 21711 |
| 10 | 32051 | 0 / 1 | 31037 | 38462 |

改后 c=10 三次是 23810 / 32680 / 32051，c=500 是 25840 / 29274 / 33445，c=1000 是 32573 / 25342 / 27809。和改前一样，单点可以差 1 万。中位数相对改前大约 **-10% 到 +23%**，没有稳定地高出计划里的 +15%～+35%。c=50 的三次很齐（34270–34626），靠近改前安静对照的 3.5–3.8 万，而不是更高。

原因和改前的分解一致：c≥10 时客户端握手和服务端差不多慢。栈分配占的是服务端样本。把它拿掉之后，短连接仍顶在 `connect` / `accept` / `close` 上，所以曲线形状还在，平台期没有明显上移。泄漏本身是被拿掉了：同一次 5 万请求不再把 VmSize 撑到数 GB。

`TRACE=1` 的 `make apps` 和 `curl` 一次 200 都过。`make -C tests run` 与 `make -C stlib/tests run` 在这台 Linux 上全过，包括 64KB `makecontext` 的 `st_context_unittest`（那个测试不用 `STACK`）。没有看到 128KB 栈溢出。
